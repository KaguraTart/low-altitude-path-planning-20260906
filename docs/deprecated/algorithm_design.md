# 算法设计说明

## 3.25 多维时空大规模并行规划算法

### 模块一：多维时空约束建模

**核心思想**：将三维物理空间 + 一维时间构建为四维时空网格 `(x, y, z, t)`，每个时空格表示"某飞行器在某时刻能否出现在该位置"。

- **空间离散化**：按 `dx, dy, dz` 分辨率将连续空间划分为规则网格
- **时间离散化**：按 `dt` 时间步长将规划时域离散化
- **约束表达**：
  - 空域边界 → 网格边界
  - 静态障碍物 → 所有时间步均占用的空间格
  - 动态障碍物 → 仅在特定时间步占用的时空格
  - 飞行器性能 → 邻域移动的速度/爬升率约束
  - 飞行器高度包线 → 搜索的 `iz` 范围上下界

**两级图层（正交）**：
- `SpaceTimeGrid`（bool）：**占用**——"能不能走"
- `CostGrid`（float32）：**通行代价**——"走起来多费力"

代价层由 `build_clearance_cost_grid()` 按障碍物几何自动生成：每个静态障碍物包围盒
外扩 `clearance`（默认 200m），缓冲带内代价 ×3。该图层与 occupancy 正交叠加，
效果是让规划器天然偏好远离建筑群的航路，与 3.26 的 risk 目标同向。

代价层接入 A\* 时，**启发函数按全局 `min_cost` 缩放**
（`h = 曼哈顿距离 × dt × min_cost`）。由于每条边的真实代价 `≥ dt × min_cost`，
缩放后启发函数仍是真实剩余代价的下界，**任意代价倍率下都保持可采纳性与最优解**。
`CostGrid` 增量维护 `min_cost`（只在 set 时比较区域最小值），避免每次搜索扫全量数组。

### 模块二：静态与动态避障

**静态避障**：
- 建筑物、地形、通信塔等固定障碍物
- 使用精确包围盒（AABB）标记占用网格
- 障碍物数据来源：城市 GIS、DEM 高程、通信设施台账

**动态避障**：
- 其他飞行器、鸟群、移动车辆
- 基于时间戳轨迹，线性插值获取任意时刻位置
- 每个动态障碍物带安全半径，在时空网格中标记为膨胀占用区

### 模块三：多源规划数据融合

`ObstacleDataFusion` 类实现：
- 多数据源注册（GIS、雷达、飞行计划、生态监测）
- 按优先级合并，冲突时高优先级覆盖低优先级
  （`input_loader.SOURCE_PRIORITY`：power_grid 10 > telecom/radar/flight_plan 9/8 > city_gis 7 > ecological 6 > meteorological 5 > dem 4）
- 数据去重（静态按 10m 栅格位置 + 类型，动态按 ID）
- 容错解析：单条记录缺字段只记 warning 并跳过，不中断整批
- 数据质量报告与警告

入口：`load_obstacle_set_fused()`，被 `plan_single.py` / `plan_multi.py` / `run_stress_test.py` 共用。

### 模块四：大规模并行规划引擎

`ParallelPlanner` 类实现：
- 基于 `concurrent.futures.ThreadPoolExecutor` 的多线程并行
- 按任务优先级排序，高优先级先规划
- **共享只读 `SpaceTimeGrid` + 共享只读 `CostGrid`**（P2 优化，消除每任务重建）
- 多航点任务分段规划后拼接
- **时空占用表** `SpatioTemporalOccupancyTable`（现位于 `src/planners/occupancy.py`）：
  `(ix,iy,iz,it) → {aircraft_id: {route_id}}`，支持占用登记/回滚/查询/冲突溯源，
  并可通过 `to_dense_mask()` 导出与 `SpaceTimeGrid` 同构的 4D 禁飞 bool 数组
- **冲突检测** `detect_conflicts_occupancy()`：按航线增量登记（查冲突 → 登记占用），
  每条航线只与已登记航线比较，避免 O(n²·m²) 重复比对
- **冲突避免（任务书 §五.4，`plan_batch()` 默认开启）**：
  检测 → 每对选优先级低者 → `to_dense_mask(exclude_route_id=...)` 生成掩码 →
  `SpaceTimeAStar` 在 `_get_neighbors` 中跳过禁飞格 → 串行 `mark_route` 更新占用表，
  最多 `max_conflict_rounds=3` 轮。关闭时仍**如实返回**检出的 `result.conflicts`。
  `clearance_cells()` 把 `min_separation` 换算成每轴膨胀格数（floor），
  保证"未被膨胀标记 ⇒ 某轴格距 > r ⇒ 世界距离 > min_separation"。
- **冲突协调** `resolve_conflicts()`：对每条冲突给出"延迟起飞"或"高度调整 +1 层"建议，
  延迟秒数按**对方航线真实通过冲突点的时间区间**反推，而非固定步长
- 规模验证：支持万级任务批量规划，**10/100/1000/10000 各规模残余冲突均为 0**

### 核心算法：多维时空 A*

**状态空间**：`(ix, iy, iz, it)` 四维网格坐标

**搜索策略**：
- 6 邻域空间移动（上下左右前后）+ 等待动作
- 水平移动推进 1 个时间步
- 启发函数：曼哈顿网格距离 × 时间步长 × `min_cost`（可采纳）
- 代价函数：时间步长 × `min_cost` 倍率 + 微小距离惩罚（打破平局）
- Closed set 避免重复扩展

**飞行器包线约束**（A* 直接消费飞行器性能参数）：

| 约束 | 实现 | 说明 |
|---|---|---|
| 高度下限/上限 | `_resolve_altitude_band()` 求包线 ∩ 网格 z 范围 | 限制搜索的 `iz` 边界 |
| 起终点高度预检 | `altitude_error()` | 越界直接失败并给可读原因，不做无用搜索 |
| 爬升/下降率 | `_get_neighbors()` 折算所需时间步 | 见下方阶梯式移动 |

**阶梯式垂直移动**：栅格 `dz=50m`、`dt=10s` 意味着单时间步垂直位移隐含 5 m/s，
高于多数机型升降率。若简单拒绝 `dz≠0` 的动作，升降率受限的飞行器将**完全无法
改变高度**。因此一次 `dz` 位移按
`steps = ceil(|dz| · dz / (rate × dt))` **跨多个时间步**完成，并沿途检查中间格占用；
代价相应按 `steps × dt` 累加。

**关键优化**：
- 精确包围盒障碍物标记（不浪费上方空域）
- 过期条目跳过（stale entry check）
- 速度约束过滤不可行动作
- 高度包线在邻域生成阶段即剪枝

## 3.26 智能飞行线路规划算法

> 注：气象相关功能按需求标注"气象相关的做不了"，本实现不包含气象数据融合。

### 模块一：地理管制数据融合

- 静态障碍物（建筑物、禁飞区）
- 动态障碍物（其他飞行器轨迹）
- 空域边界约束
- **不包含**：气象数据（风、雨、能见度等）

### 模块二：飞行器性能与任务约束建模

`AircraftPerformance` 类定义：
- 运动学约束：最大速度、爬升率、下降率、转弯率、加速度
- 几何约束：旋翼半径、安全裕度
- 续航约束：最大飞行时间、最大航程
- 运行高度限制

`FlightTask` 类定义：
- 航点序列（含起点、途经点、终点）
- 时间窗约束
- 任务优先级
- 多目标优化权重

**兼容性校验** `check_aircraft_compatibility()` 逐条核对：载荷、续航、最大速度、
升限，以及**每个航点的实际高度**是否落在机型工作包线内。

> 为什么要核对航点高度：`requirements.min_ceiling_m` 只表达"任务需要多高"，
> 若它与航点实际高度不一致（样例数据中 `task-003` 需求写 200m 但航点在 220m、
> 机型升限 200m），规划必然失败。放在需求校验阶段拦截，比等 A* 耗尽迭代后才
> 报"未找到可行路径"更早、更可定位。

### 模块三：多目标航线优化

`RouteOptimizer` 类实现四目标优化：

| 目标 | 说明 | 权重示例 |
|------|------|----------|
| distance | 总航程最短 | 0.2-0.4 |
| time | 总飞行时间最短 | 0.2-0.6 |
| risk | 距障碍物风险最低 | 0.1-0.5 |
| energy | 估算能耗最低 | 0.1-0.2 |

**优化流程**：
1. 时空 A* 生成初始无碰撞路径（受飞行器包线与代价层约束）
2. 三次样条插值平滑轨迹
3. 碰撞检测（平滑后若穿模则回退原始路径）
4. 性能约束修正（速度、爬升率、转弯率）
5. 多目标指标计算与加权评分
6. 生成结构化 `PlanningExplanation` 并挂到 `route.explanation`

### 模块四：航点生成与结果解释

**航点提取**：
- 按最小间距（默认 80m）采样
- 航向变化超过 15° 时插入航点
- 起点标记 takeoff，终点标记 land

**结果解释**（`PlanningExplanation`，随 JSON 的 `explanation` 字段输出）：

| 字段 | 内容 |
|---|---|
| `summary` | 一句话总结（含综合得分） |
| `score` | 综合加权得分（越低越优） |
| `objective_breakdown` | 四目标各自的加权贡献，**之和 = score** |
| `performance_margin` | 速度/爬升/下降/转弯的极限占用比例（1.0 = 打满） |
| `avoidance_count` | 航线贴近（<50m）的障碍物数量 |
| `notes` | 需复核提示：样条回退、高风险、转弯率接近极限、续航余量偏小 |

### 模块五：规划服务封装与综合评测

- 统一 `PlannedRoute` 输出格式
- 批量规划结果 `PlanningResult`
- JSON 序列化输出
- Markdown 规划报告生成（含验证章节 + 数据质量章节）
- **合法性验证**（`PathValidator`，7 维：连续性 / 静态障碍 / 动态障碍 / 高度 /
  飞行性能 / 时空占用 / 多机间隔），结果写 `validation*.json`，
  存在 ERROR 时入口脚本以退出码 2 结束
- 可视化（3D 静态图 + 交互式 HTML + 风险热力图）

## 性能指标

> **测试环境**：macOS (M-series), Python 3.11.16, 8 工作线程, A\* 单任务最大 200,000 次迭代
> **测试时间**：2026-10-08（飞行器包线约束 + 通行代价层接入后重测）
> **任务生成**：起点/终点/机型/优先级/起飞时间全部随机，4 种机型，20% 多航点任务
> **命令**：`python run_stress_test.py --scales 10 100 1000 10000 --seed 20260906 --workers 8 --compare`

### 规模压测（FULL 模式）

**累计**：11,110 条任务成功 10,114 条，**整体成功率 91.04%**（FULL 与 DISPATCH 一致）。

### 约束收紧的代价（可解释性）

| 配置 | N=1000 墙钟 | 平均最近障碍距离 |
|------|------------|-----------------|
| 无代价层（仅包线约束） | 101.6 s | 138.1 m |
| 开启代价层（默认） | 127.7 s | 196.8 m |

代价层开销 **+26%**，换来 **+59m** 平均障碍净空。

约束本身带来的搜索量增加（N=1000: 36.10s → 101.6s，约 2.8×）来自：
- **高度包线**收窄 `iz` 搜索范围，启发式在垂直方向引导变弱
- **升降率阶梯式移动**使一次 `dz` 位移跨多个时间步，路径步数与 A\* 迭代数增加

代价层自身开销已优化：165.0s → 154.6s（3D 缓存友好视图）→ **127.7s**
（`CostGrid.lookup_array()` 直取数组，消除热循环里的 Python 方法调用），合计 **1.29×**。

### P2 优化（共享时空网格）

2026-10-01 基线（尚未加入包线约束与代价层），用于量化共享网格本身的价值：

| 规模 N | 优化前墙钟 | 优化后 (FULL) | 加速比 |
|--------|------------|---------------|--------|
| 1,000  | 67.8 s     | 36.10 s       | **1.88×** |
| 10,000 | 789.6 s    | 437.31 s      | **1.81×** |

N=10000 总耗时从 **13.2 分钟降至 7.3 分钟**。内存分配从 30 GB 降至 3 MB（减少 99.99%）。

### DISPATCH vs FULL 对比

| 规模 N | FULL (s) | DISPATCH (s) | 加速比 | 成功率 |
|--------|----------|---------------|---------|--------|
| 10     | 0.4     | 0.2          | 1.75×  | 100% / 100%   |
| 100    | 19.1    | 18.0         | 1.06×  | 89% / 89%     |
| 1,000  | 129.0   | 122.5        | 1.05×  | 92% / 92%     |
| 10,000 | 1,560.0 | 1,512.8      | 1.03×  | 90.95% / 90.95% |

DISPATCH 模式（跳过 risk/heading + 起点预校验）实测提速 **1.03-1.06×**（N≥100）。原因是：
- A\* 主循环占了 90%+ 时间，risk/heading 仅占 1-3%
- 起点预校验（搜索半径 2 格）增加少量 Python 调用，而随机任务中"起点在障碍物内"占比不高，开销基本被浪费
- N=10 上加速 1.75× 是因为任务极少，规划总耗时小，预校验开销可忽略

主要价值：**节省 I/O 和报告生成开销**。

> **注意**：两模式成功率完全相同，说明起点预校验在随机任务集上未实际救回任务。
